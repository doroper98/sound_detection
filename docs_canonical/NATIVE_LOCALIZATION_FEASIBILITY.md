# iPhone 소리 위치 추정: 개발 이력과 가능성 재진단

2026-09-23 · EXP-021 · REQ-DOC-003 / SC-45 · REQ-NATIVE-024 / SC-46.

**수음 성공, 소프트웨어 검증, 실제 위치 정확도를 구분한다. 현재 iPhone의 정확한 음원 위치 추정은 입증되지 않았다. 불가능하다고 입증된 것도 아니다.** 이번 작업은 기존 구현의 감사·재현 실험·기록이며 새 iOS 알고리즘이나 IPA를 만들지 않았다. 감사 대상 코드는 `92b8c5008b1ace28b12428f8d9db9800a1feb419`다.

## 사용자 요청과 현재 우선순위

- 실제 카메라 전체 화면 위에 소리 위치·세기의 열지도, 열섬 안 주파수, 부드러운 좌우 파형을 표시한다. 빌드 5는 사용자가 설치 검사를 생략했다.
- 보정 절차가 어렵고 1/6에서 진행되지 않으며 개발이 느리다는 피드백을 받았다. 큰 안내·대기 원인·통계 보존을 개선했으나, 실기기 해결과 정확도를 합성 테스트 PASS로 대체하지 않는다.
- 사용자는 크기 차이뿐 아니라 시간차와 연속 이동 관측을 검토하고, 가능한지 면밀히 진단한 다음 실제 되는 방법을 찾으라고 요청했다. “좌우 크기가 충분히 변하지 않았다”의 물리적 원인을 명백히 찾는 작업은 아직 열려 있다.
- 먼저 지금까지 실패·개발·발견·수정 이력을 지정 문서에 보존하고 커밋·푸시·main 병합하라는 요청을 받았다. 이 병합은 위치 기능의 실기기 검증 완료 선언이 아니다.
- 가로 수음 비교는 UI·오디오 방향·AR 축을 함께 구현한 뒤 검증한다. LiDAR 지도/공간·소리 export는 [후속 계획](LIDAR_SPATIAL_EXPORT_PLAN.md)에 보류되어 있다.

## 이번 JSON으로 확정할 수 있는 것

[선택 필드와 해석](../docs/reports/2026-09-23-iphone17pro-build9-audio-only-analysis.json)은 사용자 JSON 전체를 재구성한 원본이 아니다.

- 12:04:08~12:04:23 UTC, `startControl=audioDetails`, 시작 때 카메라 false, 카메라 프레임 0. 소리·AR 대응은 0/147, 거부는 **147개 모두 cameraStopped**다. 중지 후 tracking=false라는 값만으로 내린 결론이 아니다.
- 두 채널은 48kHz로 147구간 모두 활성, 복제/분석 누락 0. 지연 후보 13/147(8.84%)이고 일부 후보는 −5 samples(−104.17µs)다. 이 값은 오른쪽 신호가 먼저 온다는 처리 신호의 부호이며, 음원 방향이나 물리 마이크 경로 차이를 바로 뜻하지 않는다.
- 회전 보정은 `spatial.calibration.phase=idle`, `step=0`, `completedSamples=0`이다. 실패한 6단계의 `diagnostics.steps`/`responses`가 없다. 따라서 **이 JSON을 실패한 회전 보정의 표본으로 분석할 수 없다.**
- `CaptureModel.start()`는 `NativeReport()`와 `spatial.start()`로 이전 결과를 초기화한다. 측정 상세의 “스테레오 수음 시작”은 카메라 없는 새 세션을 시작한다. 사용자의 실제 버튼 순서는 알 수 없지만, 실패 후 새로 시작했을 때 기록이 사라지는 경로는 코드로 확인했다.
- 마지막 구간의 −56.36/−56.43dBFS, 차이 −0.074dB, 주파수 210.94Hz, peak margin 0.00897은 **그 구간**에만 해당한다. 현재 margin 기준 0.08에 못 미쳐 ambiguous다. 이 마지막 저주파·작은 차이를 앞선 보정 실패의 원인으로 소급하지 않는다.

## “좌우 차이 부족”의 정확한 코드 조건

`RotationCalibrationDiagnostics.swift`는 각도 −25/0/+25°를 두 번 측정한 6단계의 중앙값으로 별도 직선 모델을 맞춘다. **좌우 크기 차이와 시간차를 모두 이미 사용하며, 둘 중 하나만 합격해도 보정 프로필을 만든다.**

| 판정 | 크기 차이 모델 | 시간차 모델 |
|---|---|---|
| 입력 | R−L dBFS | candidate일 때만 정수 sample lag |
| 최소 기울기 절댓값 | 0.04 dB/도 | 0.12 sample/도 |
| 각 단계 유효 표본 | 75% 이상 | 75% 이상 |
| 같은 각도 반복 오차 | 6° 미만 | 6° 미만 |
| 직선 모델 잔차 RMS | 5° 이하 | 5° 이하 |

전체 표본의 유효성, 단계별 각도 오차 <3.1°, 대역 shape 변화 <0.4도 먼저 검사한다. 지연 후보 자체에는 정규화 상관 ≥0.35, 두 번째 peak와의 차이 ≥0.08, 탐색 경계 제외 등 별도 조건이 있다.

사용자가 인용한 문구는 두 모델 모두 통과하지 못한 상황에서 **크기 차이 모델의 기울기 절댓값이 0.04보다 작을 때** 선택된다. 화면이 크기 차이만 설명하는 것은 불완전하다. 시간차 모델의 실패 이유(후보 부족·작은 기울기·반복성·잔차)는 숨겨진다. 이를 **BUG-022: 실패 문구의 방법 편향, OPEN**으로 남긴다. 시차가 구현에서 빠졌다는 의미는 아니다.

**소프트웨어 거부 조건은 확인했다. 실제 좌우 응답이 왜 작았는지의 물리적 원인은 미확정이다.** 실패한 실행의 여섯 단계 값이 없기 때문이다. 기기 후처리, 스피커 배치/반사, 실제 각도, 주파수별 상쇄, 모델/임계값 부적합을 현재 증거로 구분할 수 없다. 사용자 동작이나 세로 모드를 원인으로 단정하지 않는다.

현재 임계값은 `thresholdsPhysicallyValidated=false`인 휴리스틱이다. 예를 들어 실제 iPhone과 무관한 **간격 12cm의 이상적 무지향성 마이크, 음원 거리 1m, 자유 음장**이면 ±25°에서 역거리 감쇠만으로 생기는 좌우 크기 차이는 약 ±0.439dB다. 양끝 차이 약 0.879dB로 현재 기준의 약 2dB보다 작다. 방향 정보가 존재해도 크기 차이 문턱에 못 미칠 수 있음을 보이는 반례다. 실제 iPhone 응답 예측이나 이번 실패 원인의 입증이 아니다. 임계값을 낮춰 통과시키는 것만으로 정확도를 검증할 수 없다.

같은 실패 직후 수음을 새로 시작하지 않고 **측정 상세 → 진단 JSON 공유**하면 기존 단계별 통계가 유지된다. 이미 초기화된 보고서에서 이전 수치나 PCM을 복원할 수는 없다. 이 기록 보존의 사용성 문제를 **BUG-023: 새 세션에서 이전 실패 기록 소실, OPEN**으로 남긴다. 새 세션 초기화 자체는 기존 설계이며 이번 감사에서 수정하지 않았다.

## 처음 3D 시뮬레이션과 실제 앱은 무엇이 다른가

| 항목 | 가상 실험실 | 현재 iPhone 앱 |
|---|---|---|
| 센서 입력 | 알려진 위치의 가상 센서별 전파 지연·감쇠 PCM | 내장 Stereo polar pattern의 처리된 좌우 PCM |
| 마이크/자세 | 임의 가상 간격, 정확한 세계 좌표 | 물리 유효 간격 미교정, AR 자세·시각 자체도 검사 필요 |
| 지연 계산 | GCC-PHAT, Hann 창, peak 보간 | 평균 제거·절댓값 정규화 상호상관, 정수 lag와 peak-margin 거부 |
| 방향/위치 | 알려진 센서 기하의 시간차 격자 비용 | 경험적 크기/lag 직선 보정 후 여러 AR 방향 평면 결합 |
| 환경 | 반사·잡음·후처리·pose 오차 없는 기본 합성 | 반사·여러 소리·기기 처리·추적 오차 가능 |

`tests/acoustics.test.ts`의 독립 4관측 <21cm 검사는 분석적 시간차 fixture이며 일부 관측의 **가상 간격을 40cm로 변경**한다. 다른 `engine.test.ts`는 PCM 지연 복원과 엔진 독립성을 검사한다. 이들을 iPhone의 12cm 원시 마이크 또는 실측 3D 성공으로 설명하면 안 된다. UI의 “정답 비교” 모드는 탐지 결과가 아니다. 사용자가 당시 어느 모드를 본 것인지는 확인되지 않았다.

Apple은 내장 스테레오가 여러 마이크의 신호를 모델링하고 방향 처리를 적용해 만들어진다고 설명한다. 따라서 두 채널의 차이를 특정 두 물리 마이크의 순수 도착 시간차로 간주할 근거가 없다. 반대로 이 처리가 방향 정보를 모두 없앤다고도 단정할 수 없다. [Apple WWDC20 원문](https://developer.apple.com/videos/play/wwdc2020/10226/)

## 재현한 오프라인 실험과 실패 사례

실행: `npm run build:engine` 후 `node scripts/audit-localization-feasibility.mjs`. [결과 JSON](../docs/reports/2026-09-23-localization-feasibility-synthetic.json).

**합성 반례 실험이며 iPhone 측정이 아니다.** 기존 JS 엔진을 직접 호출하고, Swift 지연 계산은 비교용 JS로 옮겨 실행했다(Swift 바이너리 실행 아님). 각 조건 12개 seed, 48kHz/4096 samples. 64개 무작위 주파수·위상의 합성 신호, 잡음 없음. 지연 5.35 samples.

| 합성 조건 | 현재 네이티브 방식 후보 | 후보의 지연 평균 절대 오차 | 기존 GCC-PHAT의 평균 절대 오차 |
|---|---:|---:|---:|
| 300Hz~10kHz 직접음 | 12/12 | 0.350 samples | 0.016 samples |
| 100~800Hz 직접음 | 0/12(모두 보류) | 해당 없음 | 0.017 samples |
| 직접음보다 강하고 다른 지연을 가진 반사음 | 12/12 | 4.650 samples | 4.644 samples |

GCC-PHAT가 반환하는 수치는 합격 판정이 아니다. 저주파 사례는 잡음 없는 수치 실험에서 현재 거부 규칙의 한계를 보일 뿐, 일반 환경에서 GCC가 같은 정확도를 낸다는 뜻이 아니다. 강한 반사 사례에서는 **두 방법 모두 다른 경로를 따라 틀렸다.** 교체만으로 해결된다고 약속할 수 없다.

추가 반례로 방향과 무관하게 한 채널에 고정 5 sample 디지털 지연을 준 신호는 두 계산 모두 지연을 잘 찾는다. 그러나 방향 정보는 없다. 이는 Apple 처리를 재현한 것이 아니며, “지연 후보가 많다”가 “방향 정보가 있다”의 증명이 아님을 보인다.

기존 격자 엔진에 별도 합성 PCM과 **정확히 알려진 12cm 센서 기하**를 주었다. 음원은 격자 사이에 두고 추정기는 그 좌표를 받지 않는다. 서로 다른 위치·높이·축 8개(수 m 범위)의 관측에서 최고 격자 후보 오차는 약 5.2cm, 후보 4개였다. 한 자세는 후보 3306개, 같은 관측 8회 반복도 후보 1155개·최대 퍼짐 5.3m였다. 반복 복제는 독립 증거가 아니며 비용 합 때문에 띠만 얇아질 수 있다. **다양한 기하가 있으면 원리상 수렴하지만, 손목만 돌린 iPhone의 실제 성능 증거는 아니다.**

## 실제 가능한 경로를 판단하는 기준

1. **내장 스테레오의 방향 정보부터 확인한다.** 원본 실패 실행의 각도별 레벨/lag/반복 통계가 최소 증거다. 현재 요약 JSON에는 PCM·주파수별 복소 채널 관계가 없어 새 지연/위상 알고리즘을 실측에 소급 적용할 수 없다.
2. **처리된 채널에 맞는 방향 모델을 검토한다.** 전체 대역 크기 차이·단일 정수 lag만으로 실패했다고 끝내지 않는다. 주파수별 크기/위상 관계, 신뢰할 수 있는 대역의 시간차, 반복 관측을 후보로 비교한다. 상대 전달함수 기반 방향 추정의 실제 데이터 연구가 있지만 iPhone Stereo에 대한 검증은 별도다. [DP-RTF 연구](https://arxiv.org/abs/1509.03205)
3. **방향 모델은 별도 각도로 검증한다.** 학습에 쓴 −25/0/+25°를 다시 맞춘 것만으로 통과시키지 않는다. 다른 각도·반복·음량·신호·공간에서 좌우 부호와 오류/거부율을 함께 평가한다. 현재 직선 기준이 거부한 이유와 새 방법의 정확도 개선을 분리한다.
4. **검증된 방향에 이동 기하를 결합한다.** 방향 정보와 정확한 자세/이동이 있어야 누적이 유용하다. 수평 방향만 얻을 때 제자리 회전은 거리를, 모두 평행한 방향 평면은 높이를 결정하지 못한다. 충분한 이동·기울기와 고정된 같은 음원이 필요하다. 회전과 binaural 단서를 함께 학습한 연구는 있으나 이 앱의 실기기 보장은 아니다. [SLfM 연구](https://arxiv.org/abs/2303.11329)
5. **내장 입력으로 필요한 오차 범위가 안 나오면 입력 장치를 바꾼다.** 공통 샘플 클록·알려진 배열 기하·채널별 신호가 확보된 외부 마이크 배열은 원래 물리 TDOA 방식에 맞는 대안이다. 실제 iPhone 연결/채널 제공/동기화와 정확도 검증이 필요하며 장비 구매나 성능을 확정하지 않았다. [GCC 위치 추정 원리](https://www.mathworks.com/help/phased/ug/source-localization-using-generalized-cross-correlation.html)

LiDAR는 관측 자세·표면 기하에 도움을 줄 수 있지만 소리의 방향 정보나 반사 제거를 자동 제공하지 않는다. 보이는 물체·화면 중앙을 음향 정답으로 주입해서 성공처럼 보이게 하지 않는다.

## 이번 기록의 완료 범위와 다음 증거

- 완료: 기존 이력 연결, build9 세션 성격 판독, 실패 문구를 만드는 코드 조건, 두 지연 알고리즘 차이와 합성 반례의 재현, 가능한 접근의 전제 정리.
- 미완료: 실제 실패한 6단계의 좌우 응답이 작은 물리 원인, 실제 기기의 주파수별 방향 식별 가능성, 기기/음향 교정, 알려진 정답에 대한 위치 오차, 일반적인 소리·방에서의 성능.
- 다음에 필요한 자료: **같은 실패 실행**의 `spatial.calibration.diagnostics.steps` 및 `responses` 전체. 기존 JSON의 마지막 구간으로 이를 대체하지 않는다. 추가 주파수별 분석은 별도 계측과 사용자 동작을 최소화하는 설계부터 검토한다. 이번 문서 병합을 새 계측 구현이나 실패 해결로 기록하지 않는다.
